## Major

- [ ] **M1. AC6 재연결 성공 시 동작 정의 누락 (Round 1 Major 미해결)**
  - `docs/plans/44-ai-interview-websocket.md`의 75행에 `<!-- 재연결 성공 시 동작(이전 질문 재표시 vs 새 질문 대기)은 백엔드 협의 후 결정 예정 -->` 주석만 남겨져 있어, 재연결 성공 경로에 대한 실제 구체적 AC(Then)가 정의되지 않았습니다.
  - 재연결 성공 시 클라이언트가 이전 질문을 백엔드에 재요청해야 하는지, 백엔드가 자동으로 마지막 질문을 재전송하는지, 아니면 새로운 질문을 대기해야 하는지 구체적인 동작 명시가 없으면 테스트 작성 및 기능 구현이 불가능합니다.

- [ ] **M2. 상태 머신 다이어그램과 AC 간 재연결(Reconnecting) 상태 불일치 (Round 1 Minor 미해결 및 설계 오류)**
  - 135행 상태 열거형에 여전히 `RECONNECTING` 상태가 누락되어 있고, 151행 상태 머신 다이어그램에서도 `SUBMITTING ├─[연결 끊김]→ ERROR`로만 표시되어 있습니다.
  - AC6에서는 "재연결 중임을 알리는 배너 또는 스피너가 표시된다"고 명시되어 있으나, 상태 머신 상에서 `ERROR` 상태로 즉시 전이하게 되면 에러 화면으로 이동할지 아니면 면접 진행 화면에서 재연결 배너만 띄울지 UI 동작이 충돌합니다.
  - `ERROR` 상태에서 재연결을 시도하고 성공 시 복구하는 흐름이 상태 머신 다이어그램과 열거형에 반영되어야 합니다 (예: `RECONNECTING` 상태 추가 혹은 `SUBMITTING/QUESTION ──[연결 끊김]──> RECONNECTING ──[재연결 성공]──> SUBSCRIBED/QUESTION` 전이 추가).

- [ ] **M3. WebSocket / STOMP 환경에서의 HTTP 401 인증 오류 감지 불가능 (AC5 설계 결함)**
  - AC5는 "인증 오류(401) 또는 연결 실패 시 ... 토큰 만료인 경우 로그인 페이지로 리다이렉트된다."라고 규정하고 있습니다.
  - 하지만 브라우저 표준 WebSocket API는 연결 핸드쉐이크 단계에서 발생하는 HTTP status code(예: 401 Unauthorized)를 JavaScript 레이어에서 읽을 수 없습니다 (`onerror` 및 `onclose` 이벤트에는 HTTP 응답 헤더나 바디 정보가 포함되지 않고 단순히 1006 등의 종료 코드만 전달됨).
  - 따라서, HTTP 401 에러를 클라이언트가 직접 감지하여 분기 처리하는 것은 기술적으로 불가능합니다.
  - 이 문제를 해결하기 위해 백엔드에서 STOMP `CONNECT` 프레임 처리 도중 인증 실패 시 STOMP `ERROR` 프레임에 특정 에러 코드/메시지를 실어 전달하거나, WebSocket Close Event의 커스텀 close code(예: 4401)를 활용하는 스펙을 합의하고 AC에 구체적으로 명시해야 합니다.

- [ ] **M4. STOMP Destination 경로에 동적 패스 파라미터 사용 시의 백엔드 지원 여부 및 스펙 모호성 (AC3 설계 결함)**
  - AC3에서 답변 제출 경로가 `/app/interviews/{interviewSessionId}/answers`로 명시되어 있습니다.
  - STOMP 프로토콜에서 목적지(Destination) 경로에 동적 패스 파라미터(`{interviewSessionId}`)를 포함하는 경우, 브로커 환경(Spring WebSocket, RabbitMQ 등) 설정에 따라 라우팅 및 매핑이 복잡해질 수 있습니다. 일반적으로 STOMP 메시지 전송은 `/app/interviews/answers`와 같은 정적 경로로 보내고, `interviewSessionId`는 메시지 본문(Payload)에 포함하는 방식이 훨씬 더 흔하고 설계상 명확합니다.
  - 만약 동적 패스 파라미터를 그대로 사용하고자 한다면 백엔드와의 지원 가능 여부 확인이 선행되어야 하며, 그렇지 않다면 메시지 페이로드에 세션 ID를 포함하는 형태로 대안 기획이 필요합니다.

## Minor

- [ ] **N1. AC1 Then의 상태 전이 및 UI 관점 미분리 (Round 1 Minor 미해결)**
  - AC1 Then에 여전히 `화면 상태가 CONNECT → SUBSCRIBE → START 순서로 전이된다.`라는 기술적/구현 세부사항이 포함되어 있어 테스트의 관심사 분리가 되지 않습니다.

- [ ] **N2. AC5 인증 오류와 네트워크 오류 분리 미이행 (Round 1 Minor 미해결)**
  - 인증 오류와 네트워크 오류(단순 연결 실패)는 에러 처리 흐름(로그인 리다이렉트 vs 에러 메시지 표시 후 화면 복귀)이 확연히 다름에도 여전히 단일 AC5에 묶여 있습니다. 두 흐름을 별개의 AC(예: 인증 실패 케이스, 네트워크 장애 케이스)로 분리해야 가독성이 향상됩니다.

- [ ] **N3. 답변 제출 중이 아닌 '질문 대기' 혹은 '답변 입력 중' 상태에서의 연결 끊김 대응 누락**
  - AC6은 "답변 제출 중(제출 버튼 클릭 후 `ANSWER_ACCEPTED` 대기 중) 연결 끊김"만 다루고 있습니다.
  - 면접관이 질문을 하고 사용자가 답변을 타이핑하고 있는 상태(`QUESTION` 상태)에서 네트워크가 끊겼을 때의 자동 재연결 시도와 배너 표시 여부, 그리고 사용자가 이미 입력 중이던 답변 텍스트 보존 여부가 명시되지 않았습니다.

- [ ] **N4. 입력 글자 수 제한 및 빈 답변 유효성 검사 상세 부족 (AC7)**
  - 답변 입력 영역에 대한 최대 글자 수(예: 1000자 등) 제한 정책이 언급되지 않아 과도한 텍스트 입력 시의 방어 코드가 기획에서 누락되었습니다.
  - "답변을 입력해 주세요"라는 유효성 검사 메시지가 표시된 후, 사용자가 다시 입력을 시작하거나 다른 행동을 할 때 이 메시지가 언제 클리어되는지에 대한 UX 디테일이 생략되었습니다.

- [ ] **N5. 컴포넌트 언마운트 시 WebSocket 연결 해제 보장 정책 누락**
  - 지원자가 면접 진행 중에 브라우저 뒤로가기를 누르거나 다른 탭으로 이동(컴포넌트 언마운트)할 때, 활성화되어 있던 WebSocket/STOMP 연결이 적절히 disconnect 처리되는지 명시해야 리소스를 방지할 수 있습니다 (메모리 및 연결 누수 방지).
