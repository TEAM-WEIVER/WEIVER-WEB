# [#102] 구직자 계정 관리 및 문의 페이지 API 연동

## 브리핑 결론

- **경로:** 표준 경로. 신규 API 연동과 인증·개인정보 처리(비밀번호·회원 탈퇴)를 포함한다.
- **현재 단계:** 기획. 화면 디자인은 이후 전달될 Figma를 기준으로 확정한다.
- **기존 상태:** `/applicant/mypage`는 로그아웃만 제공한다. 로그인 화면의 `비밀번호를 잊으셨나요?`는 아직 이동 동작이 없다.
- **보안 원칙:** 비밀번호·인증번호·이메일 검증 토큰을 Zustand, localStorage, sessionStorage에 저장하지 않는다. 폼 로컬 상태에서만 보유하고 화면 이탈·완료 시 폐기한다.

## 범위

1. 로그인한 구직자의 비밀번호 변경 및 회원 탈퇴
2. 비로그인 구직자의 이메일 인증 기반 비밀번호 재설정
3. 로그인한 구직자의 문의 작성·제출
4. 가입 약관 및 CSRF·토큰 재발급·로그아웃 계약의 현행 API 재검증

제외: 문의 목록/상세 조회, 기업 회원용 계정 관리, 디자인에 명시되지 않은 프로필 편집.

## User Stories

### US1. 로그인 상태 비밀번호 변경

**US:** 로그인한 구직자로서, 현재 비밀번호를 확인한 뒤 새 비밀번호로 변경하고 싶다. 왜냐하면 내 계정을 안전하게 유지해야 하기 때문이다.

### US2. 회원 탈퇴

**US:** 로그인한 구직자로서, 탈퇴 영향을 확인한 뒤 계정을 탈퇴하고 싶다. 왜냐하면 더 이상 서비스를 사용하지 않을 때 계정 처리를 직접 통제해야 하기 때문이다.

### US3. 비밀번호 재설정

**US:** 비로그인 구직자로서, 이메일 인증을 거쳐 새 비밀번호를 설정하고 싶다. 왜냐하면 비밀번호를 잊어도 계정을 안전하게 복구해야 하기 때문이다.

### US4. 문의 제출

**US:** 로그인한 구직자로서, 문의 제목과 내용을 제출하고 결과를 확인하고 싶다. 왜냐하면 서비스 이용 중 문제가 생겼을 때 도움을 요청해야 하기 때문이다.

## Acceptance Criteria

### AC1. 로그인 상태 비밀번호 변경 성공

- **Given:** 유효한 Access Token으로 로그인한 구직자가 계정 관리 화면에 있다.
- **When:** 현재 비밀번호, 정책에 맞는 새 비밀번호, 일치하는 새 비밀번호 확인을 한 화면에서 입력해 제출한다.
- **Then:** `PATCH /api/auth/applicants/me/password`에 세 값을 전송한다. 서버가 기존 Refresh Token을 무효화한 성공 응답 뒤 클라이언트는 `clearAccessToken()`으로 메모리 Access Token과 sessionStorage role만 제거하고, 성공 토스트 후 로그인 화면으로 이동한다.

### AC2. 로그인 상태 비밀번호 변경 실패

- **Given:** 비밀번호 변경 폼에 있다.
- **When:** 필수값 누락·새 비밀번호 규칙 위반·확인 불일치이거나 API가 현재 비밀번호 불일치/서버 오류를 반환한다.
- **Then:** 입력 오류와 API 오류는 토스트로 명확히 표시하고, 입력값을 보존한 채 현재 화면에 머문다. 실패 시 세션과 화면 이동은 변경하지 않는다.

### AC3. 회원 탈퇴 성공

- **Given:** 유효한 Access Token으로 로그인한 구직자가 탈퇴 확인 UI를 열었다.
- **When:** 디자인에 정의된 최종 확인 행동을 완료한다.
- **Then:** `DELETE /api/auth/applicants/me`를 호출하고, 성공하면 로컬 Access Token을 제거한 뒤 공개 시작 또는 로그인 화면으로 이동한다.

### AC4. 회원 탈퇴 실패 또는 취소

- **Given:** 구직자가 탈퇴 확인 UI를 열었다.
- **When:** 취소하거나 API가 인증/서버 오류를 반환한다.
- **Then:** 취소 시 API를 호출하지 않고 UI를 닫으며, 실패 시 로그인 상태와 현재 화면을 유지하고 오류를 표시한다. 인증 갱신 실패 시 기존 보호 라우트 정책을 따른다.

### AC5. 비밀번호 재설정 이메일 발송 및 인증 성공

- **Given:** 비로그인 사용자가 비밀번호 재설정 화면에 있다.
- **When:** 유효한 이메일로 인증번호 발송을 요청하고, 수신한 6자리 인증번호를 제출한다.
- **Then:** 순서대로 `POST /api/auth/applicants/password/email/send`, `POST /api/auth/applicants/password/email/verify`를 호출한다. 발송 성공 상태는 계정 존재를 드러내지 않는 중립 문구로 안내하고, 검증 성공 후에만 새 비밀번호 설정 단계로 진행한다.

### AC6. 비밀번호 재설정 완료

- **Given:** 이메일 인증이 성공해 해당 화면의 로컬 상태에 이메일과 verificationToken이 있다.
- **When:** 정책에 맞고 서로 일치하는 새 비밀번호를 제출한다.
- **Then:** `PATCH /api/auth/applicants/password`에 `email`, `verificationToken`, `newPassword`, `newPasswordConfirm`을 전송하고, 성공 안내 후 로그인 화면으로 이동한다.

### AC7. 비밀번호 재설정 오류

- **Given:** 비밀번호 재설정 흐름 중이다.
- **When:** 이메일 형식/인증번호 형식이 틀리거나 인증번호 검증·비밀번호 변경 API가 실패한다.
- **Then:** 이메일·6자리 인증번호·비밀번호 형식 오류를 요청 전에 표시하고, API 실패 시 현재 단계에 머물러 재시도할 수 있게 한다. 공개 API 호출은 `skipAuthorization: true`, `skipAuthRetry: true`로 Access Token 첨부와 401 재발급을 막는다. 인증번호·verificationToken·비밀번호를 영속 저장하지 않는다.

### AC8. 문의 제출 성공

- **Given:** 유효한 Access Token으로 로그인한 구직자가 문의 작성 화면에 있다.
- **When:** 제목과 내용을 입력해 제출한다.
- **Then:** `POST /api/inquiries`에 `{ title, content }`를 전송하고 성공 상태를 표시한다. 중복 제출이 발생하지 않도록 요청 중 제출 제어를 비활성화한다.

### AC9. 문의 제출 오류

- **Given:** 문의 작성 화면에 있다.
- **When:** 제목/내용이 비어 있거나 API가 인증/서버 오류를 반환한다.
- **Then:** trim한 제목/내용의 빈 값, 제목 100자 초과, 내용 2,000자 초과는 요청 전에 안내하고, 실패 시 작성 내용을 유지한 채 오류와 재시도 수단을 표시한다.

### AC10. 공통 인증 계약 회귀 확인

- **Given:** 상태 변경 API를 호출하거나 Access Token이 만료된 상태다.
- **When:** CSRF가 필요한 요청 또는 401 응답이 발생한다.
- **Then:** 기존 `apiRequest`는 `/api/auth/csrf` 토큰을 `X-XSRF-TOKEN` 헤더로 전송하고, 보호 요청의 401에서만 `/api/auth/reissue` 후 원 요청을 한 번 재시도한다. `POST /api/auth/logout`은 Bearer 인증으로 호출하고, 로그아웃·비밀번호 변경·탈퇴의 성공 응답 때만 `clearAccessToken()`을 호출한다.

### AC11. 회원가입 약관 계약 회귀 확인

- **Given:** 구직자 회원가입 1단계가 성공해 signupToken을 보유하고 약관 동의 화면에 있다.
- **When:** 필수 약관과 선택 약관의 동의 상태를 제출한다.
- **Then:** 내부 Route Handler `/api/auth/signup/complete`가 실제 `POST /api/auth/applicants/signup/agreements`에 `signupToken`과 6개 agreements 필드를 전달하고, 성공 응답의 `accessToken`, `role`을 기존 로그인 세션 처리와 동일하게 반영한다.

## API 연동 매핑

| 기능                 | 메서드·엔드포인트                                 | 인증          | 요청                                                              |
| -------------------- | ------------------------------------------------- | ------------- | ----------------------------------------------------------------- |
| 로그인 비밀번호 변경 | `PATCH /api/auth/applicants/me/password`          | Bearer + CSRF | `currentPassword`, `newPassword`, `newPasswordConfirm`            |
| 회원 탈퇴            | `DELETE /api/auth/applicants/me`                  | Bearer + CSRF | 없음                                                              |
| 재설정 인증번호 발송 | `POST /api/auth/applicants/password/email/send`   | 공개 + CSRF   | `email`                                                           |
| 재설정 인증번호 검증 | `POST /api/auth/applicants/password/email/verify` | 공개 + CSRF   | `email`, `code`(6자리)                                            |
| 비밀번호 재설정      | `PATCH /api/auth/applicants/password`             | 공개 + CSRF   | `email`, `verificationToken`, `newPassword`, `newPasswordConfirm` |
| 문의 제출            | `POST /api/inquiries`                             | Bearer + CSRF | `title`(최대 100), `content`(최대 2,000)                          |

## 구현 설계 초안

- `src/lib/applicant-account-api.ts`: 계정 변경·탈퇴·비밀번호 재설정 API 타입과 호출을 분리한다.
- `src/lib/inquiry-api.ts`: 문의 요청 DTO와 제출 함수를 둔다.
- `src/schemas/`: 계정 설정용 비밀번호 정책(영문·숫자·특수문자 조합, 8~14자)을 재사용 가능한 schema/helper로 둔다. 회원가입의 기존 8~64자 정책은 변경하지 않는다.
- `/applicant/mypage`: Figma 정보구조에 맞춰 계정 관리 진입점·탈퇴 확인 UI를 확장한다.
- 비밀번호 재설정과 문의의 정확한 URL, 단계 분리 여부, 성공 후 이동 위치는 Figma 전달 후 확정한다. 현재 로그인 폼의 `비밀번호를 잊으셨나요?`는 확정 URL로 연결한다.
- 토큰 재발급과 CSRF는 기존 `apiRequest` 경로를 재사용한다. Swagger의 CSRF 계약상 모든 상태 변경 요청은 CSRF 토큰·헤더를 사용한다. 공개 재설정 3개 호출은 `skipAuthorization: true`, `skipAuthRetry: true`로 명시해, 브라우저에 남은 Access Token을 보내거나 공개 401을 재발급 흐름으로 바꾸지 않는다.
- 비밀번호 정책은 서버 정규식 `^(?=.*[A-Za-z])(?=.*\\d)(?=.*[!@#$%^&*()_+\\-={}:;\"'<>,.?/]).{8,64}$`을 공유 schema로 적용한다. 서버 검증은 최종 기준으로 유지한다.

## 화면·디자인 확인 대기 항목

### Figma 반영 — 마이페이지·계정 설정

- 마이페이지([1831:4941])는 `계정 설정`과 `로그아웃`을 별도 카드로 노출한다. 계정 설정 카드는 이메일·비밀번호 설정 설명과 우측 화살표를 제공하는 전체 클릭 가능 진입점이다.
- 계정 설정은 두 Figma 상태([1836:1758], [1836:1700])를 하나의 제출 폼으로 합친다. 읽기 전용 이메일, 현재 비밀번호, 새 비밀번호, 새 비밀번호 확인과 비밀번호 규칙 안내를 한 화면에 표시한다.
- 현재 비밀번호 확인용 API는 없으므로 중간 검증 단계를 두지 않는다. 세 비밀번호를 최종 `PATCH /api/auth/applicants/me/password` 요청으로 검증한다.
- 새 비밀번호 확인 불일치, 8~14자 규칙 위반, 현재 비밀번호 불일치 및 서버 오류는 필드 테두리 전환 대신 화면 상단/우측의 `role=alert` 토스트로 즉시 안내한다. 오류 후에도 입력값은 보존한다.
- 회원 탈퇴는 계정 설정 하단에 파괴적 동작임을 분명히 하는 빨간 버튼으로 추가한다. 클릭 후의 확인 UI와 문구는 프로젝트의 `ConfirmModal` 패턴으로 구성한다.

### 남은 디자인 확인 항목

1. 비밀번호 재설정이 단일 화면 단계형인지, 이메일 인증/새 비밀번호가 분리된 페이지인지
2. 비밀번호 재설정 성공 상태와 로그인 페이지 이동 문구

### Figma 반영 — 문의

- 지원자 사이드바에서 프로필 아이콘 바로 위의 `MessageCircle` 아이콘으로 `/applicant/inquiries/new`에 진입한다.
- 문의 페이지([1844:1538])의 기본 상태는 `문의사항 작성` 카드가 접힌 상태다. 카드를 누르면 제목·내용 입력 폼을 확장하고, 다시 누르면 접는다.
- 제목은 최대 100자, 내용은 최대 2,000자로 제한한다. 빈 값·길이 초과·API 오류는 토스트로 안내하고 작성값은 보존한다.
- `POST /api/inquiries` 성공 시 입력을 비우고 `문의가 접수되었습니다.` 토스트를 표시한다.

### 디자인·API 불일치

- Figma의 새 비밀번호 안내는 `영문·숫자·특수문자`, `6자 이상 14자 이하`로 표기되어 있으나, 계정 설정 화면의 제품 규칙은 **8~14자**로 확정한다. 서버는 8~64자를 허용하므로, 클라이언트가 더 좁은 범위를 사전 검증한다. 화면 안내는 `최소 1자 이상 영문, 숫자, 특수문자가 들어가야 합니다.`와 `8자 이상 14자 이하여야 합니다.`로 변경한다.

## 검증 계획

- Playwright + MSW: AC1~AC11의 성공·핵심 실패 흐름을 사용자 역할/레이블 기반 셀렉터로 작성한다. 미가입 이메일도 발송 성공과 같은 UI를 보이는지 포함한다.
- Vitest + RTL: API 요청 매핑, 서버 정규식과 일치하는 비밀번호 검증, 중복 제출 차단, 성공 때만 토큰 정리되는지, 공개 재설정 API의 Authorization 미첨부·401 재발급 미시도를 검증한다.
- 수동 점검: 실제 이메일 발송·코드 수신은 `docs/manual-tests/102-구직자-계정-관리-문의.md` 체크리스트로 분리한다.
- 구현 완료 후 `pnpm lint:check`, `pnpm typecheck`, 관련 테스트와 실제 브라우저 검증을 수행한다.
