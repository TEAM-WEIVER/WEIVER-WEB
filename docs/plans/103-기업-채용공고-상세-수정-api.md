# [#103] 기업 채용공고 상세·수정 화면 및 API 연동

## 배경과 목표

기업 담당자가 지원자 목록에서 자신이 생성한 채용공고의 전체 데이터를 조회하고, 기존 생성 폼에서 수정·삭제할 수 있게 한다. 기존 생성과 지원자·리포트 URL은 보존한다.

## 사용자 스토리

**US1:** 기업 담당자로서, 지원자 목록의 공고 수정을 선택해 공고 정보를 확인하고 싶다. 왜냐하면 지원자 관리 흐름을 끊지 않고 공고를 관리해야 하기 때문이다.

**US2:** 기업 담당자로서, 기존 공고의 모든 입력값을 수정해 저장하고 싶다. 왜냐하면 변경된 채용 조건과 메일 템플릿을 정확하게 반영해야 하기 때문이다.

**US3:** 기업 담당자로서, 더 이상 사용하지 않는 공고를 확인 후 삭제하고 싶다. 왜냐하면 운영 목록을 최신 상태로 유지해야 하기 때문이다.

## 수용 기준

### AC1. 공고 수정 화면 조회

- **Given:** 기업 담당자가 지원자 목록(`/corporate/recruitment/{jdId}`)에서 공고 수정을 선택했다.
- **When:** 유효한 양의 정수 `jdId`의 `/corporate/recruitment/{jdId}/edit`에 진입한다.
- **Then:** 로딩 상태 후 `GET /api/job-postings/{jdId}`의 최신 응답으로 제목·마감일·직무·소개·자격·우선순위·기술 스택·메일 템플릿을 폼에 복원한다.
- **Then:** `jdId`가 양의 정수가 아니면 API 요청을 보내지 않고 오류 상태를 표시한다.

### AC2. 수정과 전체 스냅샷 저장

- **Given:** 공고 조회에 성공해 폼이 현재 서버 데이터로 초기화됐다.
- **When:** 담당자가 값을 바꾸고 저장한다.
- **Then:** 제목, 실제 달력 날짜 형식의 마감일, 직무, 세부 직무, 메일 제목·내용을 검증하고, 유효하면 `PUT /api/job-postings/{jdId}`에 `multipart/form-data`를 전송한다.
- **Then:** FormData의 `updateDTO` 파트는 `application/json` Blob이며, 선택값의 빈 문자열·빈 배열까지 포함한 전체 공고 상태와 `isEmailBannerDeleted: false`를 담고 `emailBannerImage` 파트는 보내지 않는다.
- **Then:** 성공 시 `router.replace('/corporate/recruitment/{jdId}?refresh={timestamp}')`로 지원자 목록을 연다. 목록 페이지는 `refresh` 검색 파라미터를 `ApplicantListView`의 `key`로 넘겨 새 인스턴스를 마운트하고 지원자 API를 다시 요청한다. 이후 대시보드 진입도 기존 훅의 마운트 요청으로 최신 공고 목록을 표시한다.

### AC3. 조회·수정 실패

- **Given:** 공고 조회 또는 수정 요청이 실패한다.
- **When:** 화면이 응답을 처리한다.
- **Then:** 사용자가 이해할 수 있는 실패 안내를 표시하고, 실패한 수정은 입력값을 유지해 재시도할 수 있다.

### AC4. 공고 삭제 확인 및 완료

- **Given:** 공고 수정 화면이 표시되어 있다.
- **When:** 담당자가 삭제를 선택하고 확인 대화상자에서 확정한다.
- **Then:** `DELETE /api/job-postings/{jdId}`를 호출하고 성공하면 `router.replace('/corporate/dashboard')`로 이동한다. 대시보드는 재조회되어 삭제된 공고를 표시하지 않고, 브라우저 뒤로가기로 삭제된 공고 수정 화면으로 돌아가지 않는다.
- **Then:** 취소하면 삭제 요청을 보내지 않고 수정 화면을 유지한다.

### AC5. 삭제 실패

- **Given:** 삭제 확인 대화상자가 열려 있다.
- **When:** 담당자가 삭제를 확정했지만 API가 실패한다.
- **Then:** 실패 안내를 표시하고 대화상자를 닫거나 재시도할 수 있으며 조회된 공고 데이터는 유지한다.

### AC6. 기존 기업 기능 회귀 방지

- **Given:** 대시보드, 지원자 목록·상세·메일, 매칭 리포트 기능이 존재한다.
- **When:** 공고 수정 기능을 추가한다.
- **Then:** 기존 지원자 목록 URL(`/corporate/recruitment/{jdId}`), 대시보드·알림의 해당 링크, 리포트 URL(`/corporate/recruitment/{jdId}/applicants/{publicId}/report`) 및 API 요청 경로가 변경되지 않는다.

## 화면과 컴포넌트 설계

| 위치                                                            | 책임                                                                     |
| --------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `recruitment/[jdId]/page.tsx`                                   | 기존 지원자 목록 URL을 유지하고 공고 수정 링크를 제공한다.               |
| `recruitment/[jdId]/edit/page.tsx`                              | URL 파라미터를 검증하고 공고 수정 화면을 렌더링한다.                     |
| `recruitment/[jdId]/edit/_components/job-posting-edit-view.tsx` | 조회·로딩·오류·삭제 확인을 조합한다.                                     |
| `recruitment/new/_components/job-posting-form.tsx`              | 생성/수정 공통 폼. 초기값, 모드, 저장 콜백을 받아 기존 값을 복원한다.    |
| `job-posting-form.utils.ts`                                     | 날짜·성향 정규화, 응답→초기값, create/update FormData 변환을 단일화한다. |

기존 `/corporate/recruitment/{jdId}`는 지원자 목록으로 유지한다. 그 화면의 현재 미연결 `공고 수정` 버튼을 `/corporate/recruitment/{jdId}/edit`로 연결한다.

## API 계약 매핑

| 흐름 | 메서드·경로                               | 요청                                                                                                          | 성공 처리                                               |
| ---- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 생성 | `POST /api/job-postings?isTemp={boolean}` | `requestDTO` JSON Blob + 선택 `emailBannerImage`                                                              | 대시보드 이동                                           |
| 조회 | `GET /api/job-postings/{jdId}`            | 없음                                                                                                          | `JobPostingResponseDTO`를 공통 폼 초기값으로 변환       |
| 수정 | `PUT /api/job-postings/{jdId}`            | `updateDTO` JSON Blob + 선택 `emailBannerImage`; 배너를 다루지 않는 이번 화면은 `isEmailBannerDeleted: false` | refresh query로 지원자 목록을 새 인스턴스로 열어 재조회 |
| 삭제 | `DELETE /api/job-postings/{jdId}`         | 없음                                                                                                          | 대시보드 이동·목록 재조회                               |

Swagger 계약 확인 결과 GET 응답은 `JobPostingResponseDTO`이고 날짜는 `YYYY-MM-DD`다. PUT은 생성과 달리 `updateDTO` 키를 사용하며 배열을 전달한 값으로 통째로 덮어쓴다. 선택 문자열·배열이 응답에서 누락되면 각각 `''`, `[]`로 정규화해 항상 전체 스냅샷을 만든다. GET 응답에 배너 URL이 없어 배너 변경·삭제 UI는 이번 범위에서 제외하고 기존 배너 유지 플래그만 보낸다. `isTemp`는 POST 전용 query parameter이며 PUT에는 보내지 않는다.

## 테스트 계획

1. Playwright: 수정 화면 로딩/조회 성공, `updateDTO`라는 `application/json` Blob 파트의 전체 필드·빈 배열·`isEmailBannerDeleted: false`·배너 파일 미전송, 수정 후 refresh query를 통한 지원자 목록 재요청, 삭제 취소·성공과 `replace` 이동, 각 API 실패를 라우트 목으로 검증한다.
2. Vitest + RTL: 응답 초기화·FormData 유틸, 필수값 검증, 수정/삭제 pending·오류 상태를 검증한다.
3. 회귀: 기업 대시보드와 지원자 목록·리포트의 기존 단위/E2E 테스트를 실행한다.
4. 수동: 실제 인증 세션으로 GET/PUT multipart 계약과 배너 유지 동작을 확인한다.

## 범위 제외

- 대시보드 공고 필터와 ‘더보기’의 신규 기능 구현
- 지원자 필터/메일/리포트의 UX 변경
- 배너 이미지 변경·삭제 UI와 서버 API 계약 변경
