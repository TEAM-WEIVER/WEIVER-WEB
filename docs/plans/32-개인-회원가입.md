# [#32] 개인(지원자) 회원가입

## User Story

US: 구직 활동을 시작하려는 사용자로서, 이메일과 비밀번호로 개인 계정을 생성하고 필수 약관에 동의하고 싶다. 왜냐하면 WEIVER의 AI 채용 매칭 서비스를 이용하기 위해서이다.

---

## 플로우 개요

```
/signup/account-info  →  /signup/agreements  →  /onboarding/resume  →  /onboarding/essay  →  /onboarding/portfolio
        [기본정보]              [약관동의 = 가입완료]        [이력서]               [자기소개서]           [포트폴리오]
```

- 가입 완료 시점: 약관 동의 완료 즉시. 이후 온보딩(이력서 작성)으로 바로 이동한다.
- `completion/page.tsx` — agreements 완료 후 `/onboarding/resume`으로 직접 이동하므로 도달 경로가 없다. **삭제 대상**.
- `profile-info/page.tsx` — 현 플로우에 포함되지 않는 고립 파일. **삭제 대상**.

## Acceptance Criteria

### AC1. 이메일 인증번호 전송

- Given: 사용자가 `/signup/account-info` 페이지에 있고 이메일 입력 필드에 유효한 형식의 이메일을 입력한 상태이다.
- When: "인증번호 전송" 버튼을 클릭한다.
- Then:
  - `POST /api/auth/applicants/email/send`가 `{ email }` 바디로 호출된다.
  - 5분(300초) 카운트다운 타이머가 시작된다.
  - 인증번호 입력 필드와 "확인" 버튼이 표시된다.
  - "인증번호 전송" 버튼은 전송 중 및 타이머 진행 중에 비활성화되어 중복 요청을 방지한다.

### AC2. 이메일 인증번호 검증 성공

- Given: 인증번호 전송이 완료되어 타이머가 실행 중이고, 사용자가 6자리 인증번호를 입력한 상태이다.
- When: "확인" 버튼을 클릭한다.
- Then:
  - `POST /api/auth/applicants/email/verify`가 `{ email, code }` 바디로 호출된다.
  - 서버에서 verificationToken과 email의 일치 여부를 검증한다 (백엔드 책임).
  - 응답의 `verificationToken`을 `useEmailVerification` 훅 내부 로컬 state에 저장한다 (페이지 이탈 또는 새로고침 시 소멸).
  - 타이머가 정지하고 재전송 UI가 숨겨진다.
  - 이메일 입력 필드와 "인증번호 전송" 버튼이 비활성화(읽기 전용)된다.
  - 인증번호 입력 필드 하단에 "인증 완료" 상태가 표시된다.

### AC3. 계정 정보 제출 및 1단계 완료

- Given: 이메일 인증이 완료되고, 비밀번호(8~64자, 영문·숫자·특수문자 포함)와 비밀번호 확인이 일치하는 상태이다.
- When: "다음 단계" 버튼을 클릭한다.
- Then:
  - `POST /api/auth/applicants/signup/init`이 `{ email, password, passwordConfirm, verificationToken }` 바디로 호출된다.
  - 응답의 `signupToken`을 Zustand `signup-store`의 `account.signupToken` 필드에 저장한다.
  - `/signup/agreements`로 이동한다.

### AC4. 약관 동의 및 가입 완료

- Given: 사용자가 `/signup/agreements`에 있고, 필수 약관 4개(서비스 이용약관·개인정보 처리방침·개인회원 이용약관·AI 분석 동의)에 모두 체크한 상태이다. 민감정보 처리 동의와 마케팅 수신 동의는 선택이다.
- When: "다음 단계" 버튼을 클릭한다.
- Then:
  - `POST /api/auth/applicants/signup/agreements`가 `{ signupToken, agreements: { ... } }` 바디로 호출된다.
  - 응답의 `accessToken`을 httpOnly cookie에 저장한다 (Zustand 전역 상태에 직접 저장 금지).
  - Zustand `signup-store`를 즉시 초기화(reset)한다.
  - `/onboarding/resume`으로 이동한다.

### AC5. 약관 동의 API 실패 에러 처리

- Given: 사용자가 필수 약관에 모두 동의하고 "다음 단계" 버튼을 클릭한 상태이다.
- When: `POST /api/auth/applicants/signup/agreements`가 4xx/5xx 응답을 반환한다.
- Then:
  - `/onboarding/resume`으로 이동하지 않는다.
  - 버튼 하단 또는 폼 상단에 "회원가입 처리에 실패했습니다. 잠시 후 다시 시도해주세요." 메시지가 표시된다.
  - `signupToken`은 그대로 유지되어 사용자가 재시도할 수 있다.

### AC6. 인증번호 만료 후 재전송

- Given: 인증번호를 전송한 후 5분 타이머가 만료된 상태이다.
- When: 타이머가 0에 도달한다.
- Then:
  - 인증번호 입력 필드와 "확인" 버튼이 비활성화된다.
  - "재전송" 버튼이 표시된다.
  - 사용자가 "재전송"을 클릭하면 `POST /api/auth/applicants/email/send`가 재호출되고 타이머가 재시작된다.

### AC7. 재전송 횟수 제한

- Given: 사용자가 5분 이내에 이미 인증번호를 3회 전송한 상태이다.
- When: 4번째 "재전송" 버튼을 클릭한다.
- Then:
  - API를 호출하지 않는다.
  - "인증번호 전송 횟수를 초과했습니다. 잠시 후 다시 시도해주세요." 메시지가 표시된다.
  - "재전송" 버튼이 비활성화된다.

### AC8-a. 이메일 인증번호 전송 실패

- Given: 사용자가 유효한 이메일을 입력하고 "인증번호 전송" 버튼을 클릭한 상태이다.
- When: `POST /api/auth/applicants/email/send`가 4xx/5xx 응답을 반환한다.
- Then:
  - "인증번호 전송에 실패했습니다. 잠시 후 다시 시도해주세요." 메시지가 이메일 필드 하단에 표시된다.
  - 타이머가 시작되지 않는다.
  - "인증번호 전송" 버튼이 다시 활성화되어 재시도할 수 있다.
  - 이미 가입된 이메일 여부에 따른 별도 에러 분기 없이 동일한 전송 실패 메시지로 통합 처리한다.

### AC8-b. 인증번호 검증 실패 (코드 불일치)

- Given: 인증번호 전송이 완료되어 타이머가 실행 중이고, 사용자가 인증번호를 입력한 상태이다.
- When: `POST /api/auth/applicants/email/verify`가 4xx 응답을 반환한다 (잘못된 코드 등).
- Then:
  - "인증번호가 올바르지 않습니다. 다시 확인해주세요." 메시지가 인증번호 입력 필드 하단에 표시된다.
  - `verificationToken`이 저장되지 않는다.
  - 타이머는 계속 진행된다.
  - 사용자가 올바른 코드를 재입력하여 재시도할 수 있다.

### AC9. 계정 정보 제출 실패 에러 처리

- Given: 이메일 인증이 완료되고 비밀번호가 유효하게 입력된 상태에서 "다음 단계" 버튼을 클릭했다.
- When: `POST /api/auth/applicants/signup/init`이 4xx/5xx 응답을 반환한다.
- Then:
  - "회원가입 계정 등록에 실패했습니다. 잠시 후 다시 시도해주세요." 메시지가 폼 하단에 표시된다.
  - `/signup/agreements`로 이동하지 않는다.

### AC10. 약관 미동의 시 제출 버튼 비활성화

- Given: 사용자가 `/signup/agreements`에 있고 필수 약관 중 하나 이상이 체크되지 않은 상태이다.
- When: 사용자가 "다음 단계" 버튼을 클릭하려 한다.
- Then:
  - 버튼이 `disabled` 상태이므로 클릭 자체가 불가하다.
  - 각 필수 체크박스는 blur 시점에 Zod 유효성 검사 에러가 해당 항목 하단에 표시된다.

### AC11. signupToken 없이 약관 단계 직접 접근

- Given: 사용자가 계정 정보 단계를 거치지 않고(또는 새로고침으로 signupToken이 소멸되어) `/signup/agreements`에 직접 URL 입력으로 접근한 상태이다 (Zustand `signup-store`의 `account.signupToken`이 없다). 새로고침 시 signupToken이 소멸되어 이 AC가 발동되는 것은 의도된 정책이다.
- When: 페이지 진입 직후 마운트 시점에 토큰 유무를 확인한다.
- Then:
  - 즉시 `/signup/account-info`로 리다이렉트한다.
  - API를 호출하지 않는다.

## API 연동

| AC    | 메서드 | 엔드포인트                               | 주요 요청 필드                                                                                                                                     | 주요 응답 필드                  |
| ----- | ------ | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| AC1   | POST   | `/api/auth/applicants/email/send`        | `{ email: string }`                                                                                                                                | 200 OK (바디 없음)              |
| AC2   | POST   | `/api/auth/applicants/email/verify`      | `{ email: string, code: string }`                                                                                                                  | `{ verificationToken: string }` |
| AC3   | POST   | `/api/auth/applicants/signup/init`       | `{ email, password, passwordConfirm, verificationToken }`                                                                                          | `{ signupToken: string }`       |
| AC4   | POST   | `/api/auth/applicants/signup/agreements` | `{ signupToken, agreements: { termsOfService, privacyPolicy, individualMemberTerms, aiAnalysisConsent, sensitiveDataConsent, marketingConsent } }` | `{ accessToken, role }`         |
| AC6   | POST   | `/api/auth/applicants/email/send`        | `{ email: string }`                                                                                                                                | 200 OK (바디 없음)              |
| AC8-a | POST   | `/api/auth/applicants/email/send`        | `{ email: string }`                                                                                                                                | 4xx/5xx                         |
| AC8-b | POST   | `/api/auth/applicants/email/verify`      | `{ email: string, code: string }`                                                                                                                  | 4xx                             |

> **백엔드 협의 필요**
>
> - AC4: `agreements` 요청 Body 기준 — `sensitiveDataConsent`(민감정보 처리 동의)가 API 스펙상 포함되어 있으나, 서비스 특성상 이 단계에서는 **선택** 항목으로 처리. AI 채용 매칭 서비스 핵심 기능인 `aiAnalysisConsent`는 **필수**로 유지. 백엔드에서 `sensitiveDataConsent: false` 허용 여부 확인 필요.
> - AC7: 재전송 횟수 제한(5분 내 3회)이 서버 측에서 강제되는지, 또는 클라이언트에서만 관리하는지 확인 필요. 현재 AC는 클라이언트 카운트 기준으로 작성됨.

## 컴포넌트 스펙

### 사용할 shadcn/ui 컴포넌트

- `Button` — 인증번호 전송/확인/재전송, 다음 단계
- `Checkbox` — 약관 개별/전체 동의
- `Input` — 이메일, 비밀번호, 비밀번호 확인, 인증번호

### 상태 관리

- `useEmailVerification` 훅 — 이메일 인증 전체 상태 관리
  - 내부 로컬 state: `verificationToken` (페이지 이탈/새로고침 시 소멸 — 사용자에게 새로고침 시 재인증 필요 안내)
  - 내부 로컬 state: `sendCount` (5분 내 재전송 횟수, 클라이언트 카운트 기준)
- `useTimer` 훅 — 5분 카운트다운, `isExpired` 상태 노출 (타이머 만료 시 재전송 UI 렌더링 트리거)
- Zustand `signup-store` — `account.signupToken` 저장 (account-info → agreements 단계 간 전달, 가입 완료 즉시 초기화)
- `accessToken` 저장: httpOnly cookie 방식 (Zustand 전역 상태 직접 저장 금지)
- React Hook Form + Zod — `individualAccountSchema`(비밀번호 최소 8자), `individualTermsSchema`

### 삭제 대상 파일

- `src/app/signup/profile-info/` — 삭제
- `src/app/signup/completion/` — 삭제

### 접근성 주의사항

- 인증번호 입력 필드: `aria-label="이메일 인증번호"`, `inputMode="numeric"`, `maxLength={6}`
- 필수 약관 체크박스: `aria-required="true"`, 선택 항목: `aria-required="false"`
- 타이머: `role="timer"`, `aria-live="polite"` (스크린 리더에 남은 시간 전달)
- 비밀번호 토글 버튼: `aria-label="비밀번호 표시/숨기기"`, `aria-pressed` 상태 반영
- 에러 메시지: 관련 입력 필드에 `aria-describedby` 연결
