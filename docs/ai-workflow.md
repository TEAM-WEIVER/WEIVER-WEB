자세한 다이어그램은 `docs/aiworkflow.drawio` 참고.

```
[1. 브리핑] → [2. 기획] → [3. 개발] → [4. 마무리]
```

## 경로 선택

요청 규모와 위험도에 따라 **표준 경로**와 **경량 경로** 중 하나를 선택한다.

### 표준 경로 (새 기능 + 위험 경로)

```
[1. 브리핑] → [2. 기획] → [3. 개발] → [4. 마무리]
```

### 경량 경로 (단순 수정)

```
[1. 브리핑] → [3. 개발] → [4. 마무리]
```

- 기획 단계 생략
- 교차 리뷰 생략, code-reviewer 단일 검토

### 경로 판단 기준

**반드시 표준 경로 (예외 없음)**

| 요청 유형             | 이유           |
| --------------------- | -------------- |
| 인증·로그인·토큰 처리 | 보안 위험      |
| 개인정보·민감 데이터  | 보안 위험      |
| 라우팅·권한 변경      | 접근 제어 위험 |
| 새 API 연동           | 계약 변경      |
| 새 페이지·핵심 기능   | 요구사항 복잡  |

**경량 경로 가능**

| 요청 유형               |
| ----------------------- |
| 스타일·레이아웃 변경    |
| 텍스트·문구 수정        |
| 기존 컴포넌트 내부 수정 |
| 버그 수정 (보안 무관)   |
| 리팩토링                |

## 단계 파악 기준

> **⚠️ Claude는 작업 요청을 받으면 반드시 이 표를 먼저 확인하고 진입 단계를 결정한다. 사용자가 "기획해줘", "개발해줘" 같이 특정 단계를 언급하더라도, 이슈와 브랜치가 없으면 브리핑부터 시작한다.**

| 상황                       | 진입 단계           |
| -------------------------- | ------------------- |
| 새 작업 요청, 이슈 없음    | 1. 브리핑           |
| 이슈 있음, 범위 불명확     | 2. 기획             |
| 기획 완료 또는 경량 경로   | 3. 개발             |
| 코드 완성, PR/머지 요청    | 4. 마무리           |
| 단계 명시 ("PR 올려줘" 등) | 해당 단계 직접 진입 |

## 단계별 진입 조건 & 실행

### 1. 브리핑

- **진입**: 새 작업 요청 (이슈 없음)
- **에이전트**: `git-ops`
- **실행**: 요청 파악 → 경로 선택(표준/경량) → 이슈 생성 → 브랜치 생성 (`type/#이슈번호`, main 기준, 로컬+원격)
- **⚠️ 브랜치 없이 개발 금지**: 이슈 생성 후 반드시 브랜치를 만들고 체크아웃한 뒤 개발을 시작한다. develop 브랜치에 직접 커밋하지 않는다.

### 2. 기획 (표준 경로만)

- **진입**: 이슈 있음, 구현 범위·요구사항 미정
- **에이전트**: `planner` → 다자토론 (Claude 렌즈 = `us-reviewer`)
- **실행 순서**:
  1. `planner` — US/AC/컴포넌트 스펙/API 연동 매핑 작성 → `docs/plans/#이슈번호-설명.md` 저장
  2. **다자토론(Claude × Codex × Gemini)** — 사용자가 별도 지시하지 않아도 Claude가 자동으로 시작한다.
     - Claude 렌즈: `us-reviewer` 서브에이전트 실행 (AC 완결성·에러 케이스·형식 검토) + 보안·엣지케이스
     - Codex 렌즈: 정확성·논리 비약·반례
     - Gemini 렌즈: 외부 사실·도메인 접지·현실성
  3. FAIL 시 `planner` 재작성 → 다자토론 재실행
  4. PASS 시 사람 검증
- **⚠️ `us-reviewer` 단독 실행 금지**: 반드시 다자토론 안에서 Claude 렌즈로 실행한다.
- **산출물**: `docs/plans/#이슈번호-설명.md`
- **AC 형식**:

  ```
  US: ~로서, ~하고 싶다. 왜냐하면 ~이기 때문이다.

  AC:
    - Given (전제 조건): 어떤 초기 상태에서 시작하는가?
      When  (이벤트):    사용자가 어떤 행동을 취했는가?
      Then  (결과):      그 결과 어떤 시스템 반응이 일어나야 하는가?
  ```

- **AC 작성 책임**:
  - 정상 경로(Happy Path) AC 필수
  - **에러 케이스 AC 필수** — 빈 값, 인증 실패, API 오류, 중복 등 주요 실패 시나리오 포함
  - `planner`가 에러 AC를 누락했으면 `us-reviewer`가 Major로 지적

### 3. 개발 (ATDD)

- **진입**: 기획 완료(표준) 또는 브랜치 존재(경량)
- **에이전트**: `atdd-writer`, `next-dev`, `coverage-auditor`, `code-reviewer` (+ 다자토론)
- **실행 순서**:
  1. AC 기반 Playwright 인수 테스트 작성 (`atdd-writer`) — **셀렉터는 사용자 행동 기준** (role/label/text)
  2. MSW 목 핸들러 작성 — 정상 응답 + 에러 응답 포함
  3. 구현 (`next-dev`) — 인수 테스트 통과 목표
  4. Vitest + RTL 단위 테스트 작성 (`next-dev`) — 비즈니스 로직·유틸 함수·컴포넌트 인터랙션
  5. 커버리지 확인 (`coverage-auditor`) — 70% 임계값
  6. **다자토론(Claude × Codex × Gemini)** — `code-reviewer` 검토를 다자토론으로 진행. 사용자가 별도 지시하지 않아도 Claude가 자동으로 시작한다.
     - Claude 렌즈: `code-reviewer` 서브에이전트 실행 (품질·타입 안전성·보안·컨벤션) + 보안·엣지케이스
     - Codex 렌즈: 정확성·논리 비약·반례
     - Gemini 렌즈: 외부 사실·도메인 접지·현실성
  7. **⚠️ `code-reviewer` 단독 실행 금지**: 반드시 다자토론 안에서 Claude 렌즈로 실행한다.
  8. `pnpm lint:check` + `pnpm typecheck` 통과
  9. 커밋 (`type: 설명` 한국어, 기능 단위로 분리)

### 테스트 레이어

| 레이어            | 도구               | 대상                                   | 명령어                |
| ----------------- | ------------------ | -------------------------------------- | --------------------- |
| 인수 테스트 (E2E) | Playwright         | AC 기반 사용자 흐름 전체               | `pnpm test:e2e`       |
| 단위 테스트       | Vitest + RTL       | 비즈니스 로직, 유틸, 컴포넌트 인터랙션 | `pnpm test`           |
| 커버리지          | Vitest v8          | 단위 테스트 기준 70% 임계값            | `pnpm test:coverage`  |
| 컴포넌트 테스트   | Storybook + Vitest | UI 상태·접근성                         | `pnpm test:storybook` |

- E2E: "사용자가 이 흐름을 완수할 수 있는가" 검증
- 단위: "이 함수/컴포넌트가 올바르게 동작하는가" 검증 — E2E가 커버 못하는 엣지케이스 보완
- 두 레이어가 겹치는 영역은 단위 테스트로 처리 (E2E는 느리므로 핵심 흐름만)

### 4. 마무리

- **진입**: 개발 완료, PR 생성 요청
- **에이전트**: `git-ops`
- **실행**: PR 생성 (`Closes #이슈번호`) → CI 통과 → 사람 검수 → 머지

## 교차 리뷰 (Claude × Codex × Gemini)

> 운영 상세: `docs/cmux-guide.md`, `docs/discussion-guide.md` 참고

**매 이슈가 아닌 아래 시점에만 적용한다.**

| 적용 시점                                   | 이유           |
| ------------------------------------------- | -------------- |
| 인증·권한·개인정보 흐름 구현                | 보안 위험 경로 |
| 핵심 도메인 로직 완성 (매칭, 리포트)        | 비즈니스 핵심  |
| 아키텍처 변경 (라우팅 구조, 상태 관리 전환) | 광범위한 영향  |
| 마일스톤 완료 시점                          | 전체 품질 검증 |

## 리뷰 규칙

- **Critical / Major** → 해당 단계 재실행
- **Minor** → 사람(사용자)이 수용/기각
- 리뷰 결과 저장: `docs/reviews/`
- **토론 ≠ 검증** — 비-LLM 오라클(CI, 테스트 실행)로 최종 검증
